# Phase 6 verification

The dashboard now offers a guided entry point to the real Victoria results. The lab can reopen a bookmarked pair of experiments, shows evolutionary validation beside later replay scores, and reports what happened after each switch with a link to inspect that forecast block. Historical performance remains separate from the unscored next-block recommendation.

A fresh SQLite database can be seeded with seven allowlisted Victoria records. The bundle contains only the three input series, forecast, replay, and two completed experiments needed for the demo. Import is transactional and idempotent. Conflicting IDs are reported without overwriting existing records. Browsing the demo requires no model inference.

**54 backend tests, 23 frontend tests, and the production build passed.** A fresh local server using the seeded database was verified in the browser. The guided link opened both saved experiments. The comparison reproduced MAE **10.182** for three candidates and **10.135** for two candidates on 210 matched targets. Seasonal naive remained the best fixed model at **9.821**. The new forecast scored 32 later actuals with MAE **11.83** and RMSE **14.13**. A fresh background experiment completed 8 of 8 blocks and scored 14 targets after warm-up. A public Victoria CSV imported through the file chooser and opened as the selected dataset in the lab.

The container configuration serves React and FastAPI together, uses a pinned CPU Torch wheel, runs as a non-root user, and keeps SQLite and the model cache on a persistent volume. It disables hosted investigation by default and uses the SQLite readiness endpoint for health checks. The Linux image has not been built or run because a container engine was unavailable on the verification host. The local production build and fresh-database workflow were verified. Remote deployment requires access control at ingress, and the backend uses a single worker and shared workspace. See [DEPLOYMENT.md](DEPLOYMENT.md) for commands.
